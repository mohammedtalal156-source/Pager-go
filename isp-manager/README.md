# نظام إدارة أبراج الإنترنت (داخلي — شركة واحدة)

Next.js 16 (App Router, TypeScript) · Tailwind CSS 4 · shadcn/ui · Supabase (PostgreSQL + Auth + RLS) · React Hook Form · Zod · Lucide.

> نظام داخلي لشركة واحدة. لا يوجد تسجيل عام ولا تعدد شركات. المدير وحده ينشئ حسابات الموظفين.

## التشغيل

```bash
npm install
cp .env.example .env.local   # ثم املأ القيم (لا تشارك المفتاح السري)
npm run dev
```

### مشروع Supabase الحالي

- المشروع: **TAJIR** (`iqzicolbbrrsrhykipif`) أُعيد استخدامه لهذا النظام. تطبيق TAJIR السابق نُقل كما هو إلى المخطط `tajir` (غير مكشوف للـ API)، ونسخة من تاريخ ترحيلاته وحسابه في `tajir_backup`. لم يُحذف شيء.
- الترحيلات المطبّقة: `core_schema`, `staff_bootstrap`, `private_rls_helpers`, `setup_token` (بالإضافة إلى `move_tajir_out_of_public`).
- **لا يحتاج الموقع أي مفتاح سري.** إنشاء حسابات الموظفين وتغيير كلمات المرور وإيقاف الدخول تتم عبر Edge Function اسمها `staff-admin` (`supabase/functions/staff-admin`) تعمل داخل Supabase وتتحقق بنفسها أن المستدعي مدير فعّال.
- رمز صفحة `/setup` محفوظ كـ SHA-256 فقط في `private.app_settings`، ويتوقف تلقائياً بعد إنشاء أول موظف. لتغييره: `select private.set_setup_token('<رمز جديد>');`

### النشر (Vercel)

- المشروع: `isp-manager` على Vercel، المنطقة `sin1` (قرب قاعدة البيانات في سنغافورة).
- متغيرات البيئة: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (قيم عامة)، و `STAFF_EMAIL_DOMAIN` اختياري.
- لتفعيل النشر التلقائي مع كل تحديث: Vercel → المشروع → Settings → Git → ربط مستودع GitHub `Pager-go` وفرع `isp-manager`.

### ربط Supabase (لمشروع جديد)

1. أنشئ مشروع Supabase جديداً خاصاً بالشركة.
2. طبّق ملفات `supabase/migrations/*.sql` بالترتيب (SQL Editor أو `supabase db push`).
3. **Authentication → Sign In / Providers**: عطّل *Allow new users to sign up* (لا تسجيل عام). ويمكن تعطيل *Confirm email* لأن الحسابات تُنشأ مؤكدة من المدير.
4. ضع القيم في `.env.local` (أو متغيرات البيئة في منصة النشر).
5. افتح `/setup` وأدخل `SETUP_TOKEN` لإنشاء حساب المدير الأول. الصفحة تُغلق تلقائياً بعد وجود أي موظف.

## الاختبارات

```bash
npm run test:db     # يطبّق المخطط على PostgreSQL محلي مؤقت ويختبر RLS والصلاحيات وسلامة البيانات المالية
npm run check       # typecheck + lint + test:db
```

`test:db` لا يحتاج Supabase ولا Docker: يستخدم PostgreSQL محلياً مع محاكاة بسيطة لمخطط `auth` وأدوار Supabase (`supabase/tests/00_supabase_stub.sql`).

## تصميم قاعدة البيانات (مختصر)

- **profiles**: الموظفون (مدير / موظف / محصّل) + صلاحيات دقيقة للموظف.
- **towers**, **packages**: الأبراج والباقات (أرشفة بدل الحذف).
- **subscribers**: المشترك + حقول محسوبة يديرها النظام فقط: `start_date`, `end_date`, `total_due`, `total_paid`, `balance` (الدين). رقم مشترك تلقائي يبدأ من 1001.
- **subscriptions**: كل فترة اشتراك مفوترة (مبلغها = ما يستحق على المشترك).
- **renewals**: سجل عمليات التجديد (التاريخ السابق والجديد، من نفّذ).
- **payments**: المقبوضات الفعلية فقط — الإيراد = مجموع الدفعات غير الملغاة. `request_id` فريد يمنع التكرار عند الضغط مرتين.
- **expenses**: المصروفات بالتصنيفات المطلوبة، لبرج معيّن أو عامة.
- **audit_logs**: سجل تدقيق لكل إضافة/تعديل (لا يمكن تعديله أو حذفه).

قواعد السلامة المفروضة في قاعدة البيانات نفسها (وليس في الواجهة فقط):

- RLS على كل الجداول؛ المحصّل يرى فقط المشتركين المكلف بهم؛ المستخدم بلا ملف موظف أو الموقوف لا يرى شيئاً.
- لا يمكن لأي عميل إدخال حركات مالية مباشرة — فقط عبر دوال الخادم (المرحلة 4) داخل Transaction واحدة.
- لا حذف للحركات المالية أبداً (حتى بصلاحيات الخادم)؛ التصحيح = إلغاء (void) من المدير مع ذكر السبب، ويُسجّل في التدقيق.
- الرصيد يُعاد حسابه من المصدر (مجموع الفترات − مجموع الدفعات) فلا تُحتسب دفعة مرتين.
- يبقى دائماً مدير فعّال واحد على الأقل.
- التواريخ التجارية بتوقيت Asia/Baghdad (`today_baghdad()`)، والطوابع الزمنية مخزنة `timestamptz`.
